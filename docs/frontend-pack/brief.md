## 1. What asknget is

A **multi-vendor marketplace**: many independent sellers sell to buyers in several countries, and the platform (asknget) takes a commission.
Three audiences, three frontends, all designed in one Figma file:

| Surface | Who | What they do | Design | API |
|---|---|---|---|---|
| **Storefront** | buyers (and guests) | browse, search, cart, checkout, track, return, review, wishlist, chat with sellers | complete | complete except payments |
| **Seller portal** | store owners and their team | apply (KYC), list products, inventory, orders, returns, payouts, analytics (premium), chat, team, delivery options | complete | complete |
| **Admin portal** | asknget staff | review seller applications, orders, products, returns, payouts, categories, customers, transactions | most screens designed | **partial** (section 4) |

Markets today: **South Africa (ZA, ZAR)** and **Pakistan (PK, PKR)**. A store sells in exactly one country and currency; a cart holds one market; language, timezone and
currency come from the market. Money is integer minor units (`*_cents`), never floats.

The backend (Django + django-ninja, Postgres) is organised by concern: **accounts** (registration, login with JWT, profile, addresses, saved payment methods, email OTP, WhatsApp phone
verification by QR or button), **catalog** (two-level categories, products, variants, reviews, wishlist, category requests), **discovery** (search, suggestions, recommendations),
**orders** (guest and member carts, per-seller delivery with a free-over-threshold-or-fee rule, checkout, order lifecycle, cancel, track), **returns**, **sellers** (application and KYC,
stores, private documents), **portal** (everything the seller portal calls, under `/seller/*`), **ledger** (money), **markets** (countries, languages, policies), **notifications**,
**team**, **chat**, **marketing** (banners, vouchers).

Rules the UI must respect: premium-only areas answer `403 premium_required`; seller work is scoped by store (`X-Store`); a seller cannot create categories, they request them and staff decide;
an order keeps a snapshot of what it was charged; refunds go to the original payment only.

## 2. Responsive design (there is no mobile design)

The Figma file has **desktop frames only** (1920 px wide). Until the designer delivers mobile frames, use these defaults and say so in the pull request:

- Breakpoints **360 / 768 / 1024 / 1280 px**, mobile-first, built flexibly so a mobile design can replace them.
- Navigation collapses to a drawer below 1024 px. Product and category grids: 4, 3, 2, then 1 columns.
- Wide tables (seller products, orders, customers, inventory): cards below 768 px, never a sideways-scrolling page.
- Popups and the product wizard become full-screen sheets on mobile.

## 3. Environments and the API

| Where | Base | Use it for |
|---|---|---|
| **Backend Preview** (pre-production, staging data) | origin `https://asknget-backend-git-develop-aun-syed-shahs-projects.vercel.app` | **everything you build and test**; Swagger UI at `<origin>/api/v1/docs` |
| Backend Production | origin `https://asknget-backend.vercel.app` | **never**; the owner promotes to it |

- **The contract is the live OpenAPI document**: `https://asknget-backend-git-develop-aun-syed-shahs-projects.vercel.app/api/v1/openapi.json`. Generate typed clients from it
  (for example `openapi-typescript`); do not hand-write response types. Re-fetch it at the start of every session (section 6). Facts a generator trips over:
  - **Every path already starts with `/api/v1`** and the document has no `servers` entry: set the client's base URL to the **origin only** (`API_ORIGIN`), never to `.../api/v1`.
  - 234 operations at the time of writing, each with a unique but long `operationId`; rename them in the generator's configuration if you like.
  - **The shared headers are declared** (`X-Region`, `X-Language`, `X-Timezone` on every operation, `X-Store` on `/seller/*`, `X-Cart-Token` on cart and checkout), all optional. If your copy
    shows a header named `x_cart_token` with underscores, it is an old copy: re-fetch.
  - Every operation has a `default` error response typed `ErrorResponse` (`{detail, errors?}`); many also list specific 4xx codes. Model errors once, globally.
  - The security schemes (`JWTAuth`, `OptionalJWTAuth`, `StaffAuth`, `SellerAuth`, `StoreAuth`) are all `Authorization: Bearer <access_token>`; they differ only in who is let in.
- **Demo accounts** exist on Preview: `customer@asknget.demo`, `seller@asknget.demo`, `admin@asknget.demo`. **The password is not in this folder: ask the owner** (it is a staging demo password; never use it anywhere else).
- **Free-tier infrastructure:** keep test traffic light; no loops, no load tests.
- **File uploads do not work on Preview yet** (the server's disk is read-only; object storage is not set up): avatar, product images, review and return photos, KYC documents and the category-request image
  all fail. Build the upload UI, but expect an error there and note it in `BACKEND_ASKS.md`.
- **Never** put credentials, tokens or `.env` contents in code, logs, commits or chat.

**Do not call the backend straight from the browser.** CORS is not set for any origin, and with the proxy below it never needs to be. In `next.config.mjs` add a `rewrites()` entry (check the bundled Next docs for its current form) that forwards
`/api/v1/:path*` to `${API_ORIGIN}/api/v1/:path*` and have the app call its own origin. Consequences: the backend sees the backend's host, so the market is **not** inferred from a `za.` or `pk.`
subdomain: **always send `X-Region`**, and forward `X-Language`, `X-Timezone`, `X-Store`, `X-Cart-Token` and `Authorization`. Do not use `credentials: 'include'`.

## 4. What is built, what is not

**Built and tested:** everything in the section 1 paragraph on the backend.

**Not built, do not wire (render static, empty or disabled, and tell the owner):**
- **Payments**: `POST /checkout` makes the order `pending_payment`; there is no card tokenisation or confirmation.
- **Courier, tracking number, Live Track Order**: waiting for a courier API.
- **Wallet refund** (the Return Order popup offers "Wallet"): not decided; only "Original payment" works.
- **Admin portal API gaps**: dashboard KPIs, category management (add, edit, deactivate, reorder), customers, transactions overview, application screens beyond seller-application review, account information, recent activity.
- **Customer order screens of 2026-10-14** (View Details, Order Cancel, Return Order, Track order): backend work is planned (a cancel-reasons list, card brand and last four digits on an order, an estimated delivery date, tracking fields). Build the screens from the data that exists today.

**Known backend bugs** (the backend session will fix them; tell the owner if you hit one, do not hide it): the first `POST /cart/items` from a brand-new guest returns an empty cart in its response (the item *is* saved; read `GET /cart` again with the returned `cart_token`).

## 6. Working with the backend session

The backend is built by another Claude session you cannot see or reach. The owner carries messages between you. The rules:

1. **You never edit the backend**, and you do not try to read it. Your world is this repository plus the live API.
2. **`BACKEND_ASKS.md` (in your repo)** is how you ask: one entry per ask, with the request you sent, the response you got, and what you expected. Do not guess a shape and do not add a client-side workaround for a backend bug without logging it.
3. **Start of every session:** (a) fetch the live `openapi.json`; (b) diff it against `api/openapi.snapshot.json`, which is exactly "what changed since last time"; (c) read the top of `docs/backend/api-changes.md`;
   (d) regenerate the API client; (e) replace the snapshot. If `api-changes.md` says something the diff does not show, or the reverse, tell the owner.
4. **Backend changes are additive where possible.** A breaking change is flagged `BREAKING` in `api-changes.md` with what to do; the old shape stays until you confirm.
5. **Never call Production**, and never create demo data there. Staging (Preview) can be reset: store nothing on it you cannot recreate.
6. **No secrets cross the boundary.** Tokens, passwords and keys are set by the owner in each platform's settings or a git-ignored `.env`.

## 7. Deploying the frontend: two environments that mirror the backend's

Its own GitHub repository and its own Vercel project, wired to the backend's environments like this:

| Frontend branch | Frontend site | Talks to | `API_ORIGIN` (server-side variable in the frontend's Vercel project) |
|---|---|---|---|
| `develop` | pre-production (Vercel Preview, stable `...-git-develop-...vercel.app` URL) | **backend Preview** | `https://asknget-backend-git-develop-aun-syed-shahs-projects.vercel.app` |
| `main` | production | **backend Production** | `https://asknget-backend.vercel.app` |
| your machine | `http://localhost:<port>` | **backend Preview** | the Preview origin, in the git-ignored `.env.local` |

**A frontend environment only ever talks to the backend environment next to it in this table.** Production never points at Preview and the other way round, so staging data and demo accounts can
never reach real customers. `API_ORIGIN` is a plain server variable (no `NEXT_PUBLIC_` prefix). In Vercel (the owner clicks; tell them what): import the repository as a new project, Production Branch `main`,
add `API_ORIGIN` once for *Production* and once for *Preview* with the values above (a different value per environment, never "All environments"). Nothing secret is involved.
To let the team open the pre-production site without Vercel seats, turn Vercel Authentication off for that project.
